# SEO audit — site and README

**Date:** 2026-07-29 · **Scope:** `site/` (28 built pages) and `README.md` · **Method:** static
analysis of `site/dist` after `npm run build`, plus execution of every runnable snippet published.

---

## 1. Summary

The site before this pass was two pages with a description tag and nothing else — no canonical, no
Open Graph, no structured data, no sitemap, and no content targeting any query a person actually
types. It has been rebuilt to 28 pages across two new sections, and the technical SEO layer now
exists.

| | before | after |
| --- | --- | --- |
| indexable pages | 2 | 28 |
| canonical tags | 0 | 28 |
| Open Graph / Twitter cards | 0 | 28 |
| JSON-LD entities | 0 | 28 pages × 2–3 |
| sitemap | none | `/tman/sitemap.xml`, 28 URLs |
| internal links | nav + one CTA | 518, none broken |
| titles over 62 chars | n/a | 0 (max 50) |
| descriptions outside 110–160 | n/a | 0 (range 128–151) |
| pages under 300 words | n/a | 0 (range 756–1689) |

**Every number above was measured against the built output, not asserted.**

**The largest remaining problem cannot be fixed from this repository.** The root domain,
`https://standardbeagle.github.io/`, returns **404** — the user-site repository does not exist —
so no `robots.txt` is servable for any of the eleven Pages sites on that host. See §5.

---

## 2. What was wrong, and what was done

### 2.1 No canonical URLs — *fixed*

Every page now emits `<link rel="canonical">`. The URLs are generated by a single helper
(`src/lib/site.ts`) rather than by string concatenation at each call site, which is what previously
produced inconsistent base-path handling.

The helper appends a trailing slash to directory URLs. This is not cosmetic: Astro emits
`docs/index.html`, which the host serves at `/tman/docs/` and reaches from `/tman/docs` only via a
redirect. Declaring the slash-less form canonical would mean every crawl resolves to a URL that
differs from the one the page claims for itself. **Verified: 0 canonical/served mismatches across
28 pages.**

### 2.2 No social cards — *fixed*

`og:type`, `og:site_name`, `og:title`, `og:description`, `og:url`, `og:image` (+ width, height,
alt), and the Twitter equivalents. A 1200×630 card was generated at `site/public/og.png`; before
this there was no image to serve, so every share rendered as a bare text link.

### 2.3 No structured data — *fixed*

Each page carries a JSON-LD `@graph` with:

- a `SoftwareApplication` entity for tman (category, operating systems, licence, repository, price),
- a `BreadcrumbList` matching the visible breadcrumb trail,
- a `TechArticle` or `CollectionPage` for the page itself,
- a `FAQPage` built from the same question-and-answer pairs rendered visibly on the page.

The FAQ entities are generated from the rendered content rather than written separately, so the
markup cannot describe answers the page does not actually show — which is the failure mode that gets
FAQ rich results revoked.

**Verified: all 28 pages parse as valid JSON.**

### 2.4 No sitemap — *fixed*

`/tman/sitemap.xml`, generated from the same `AGENTS` and `TOOLS` arrays the pages are generated
from, so it cannot drift out of sync with the routes. Referenced from every page via
`<link rel="sitemap">`.

Written as a 30-line endpoint rather than by adding `@astrojs/sitemap`: the integration's value is
discovering routes you did not enumerate, and here every route is already enumerated in a file the
endpoint imports.

### 2.5 Almost no indexable content — *fixed, and this is the substantive change*

Two pages cannot rank for anything. The site now has two content sections, both built from data
rather than duplicated markup:

**`/setup/` — nine per-agent guides.** Organised around the one property that determines what tman
can do: whether the agent's pre-tool hook can *replace* a shell command, only *gate* it, or does not
exist. This taxonomy was derived from vendor documentation, not assumed:

| agent | hook event | can rewrite the command? |
| --- | --- | --- |
| Claude Code | `PreToolUse` | yes — `hookSpecificOutput.updatedInput` |
| Codex CLI | `PreToolUse` | yes — same payload field names as Claude Code |
| Gemini CLI | `BeforeTool` | yes — `hookSpecificOutput.tool_input` merges over the arguments |
| opencode | `tool.execute.before` | yes — `output.args.command` is mutable |
| Cursor | `beforeShellExecution` | **no** — allow / ask / deny only |
| Antigravity | `PreToolUse` | **no** — `decision` of allow / deny / ask / force_ask |
| Kimi Code CLI | `PreToolUse` | undocumented — treated as a gate |
| GitHub Copilot CLI | `preToolUse` | **no** — deny only, and `toolArgs` arrives JSON-encoded |
| Aider, Amp, Windsurf, Zed, CI | — | no hook surface; PATH shims |

**`/tuning/` — fifteen per-tool guides.** Vitest, Jest, pytest, go test, dotnet test, cargo test,
Playwright, RSpec, Gradle/Maven, ESLint, Ruff, Biome, golangci-lint, tsc, Vite/webpack. Each carries
a starting cap set, a paste-ready `.tman.kdl` alias, the reasoning behind each number, and a closing
section on replacing the starting point with a measurement.

Every recommended value is labelled a **starting point derived from how the tool behaves**, not a
measurement of the reader's machine. That qualifier appears on the hub, in the cap table on each
page, and in the calibration section — a table of numbers published without it is the kind of thing
people paste into a config and then debug for an afternoon.

### 2.6 Runnable snippets were unverified — *fixed by execution*

Three of the guides publish scripts a reader will run. Publishing code that has never been executed
is the documentation equivalent of a test that reports success without doing work, so each was
extracted **from the built HTML** — not from the source — and run:

| snippet | cases run | result |
| --- | --- | --- |
| `tman-gate.sh` (Cursor, Antigravity, Kimi, Copilot) | supervisable command / unrelated command / unadopted project | deny with the correct supervised command · silent allow · silent allow |
| `tman-gemini-hook.sh` (Gemini CLI) | rewrite / advice-only / ignored | correct `tool_input` rewrite · advice passed through · silence |
| opencode plugin (Node) | bash+supervisable / bash+unrelated / non-bash tool | rewritten · untouched · untouched |

This caught two real defects before publication: an unquoted `${verdict:-{\}}` fallback that made
the gate adapter fail on an empty verdict, and a test harness that ran inside a supervised tree and
so exercised tman's no-double-supervision path rather than the plugin.

### 2.7 Internal linking — *fixed*

518 internal links, **zero broken**, verified against the built file tree. Every guide links to its
hub, its siblings, and the other section; the home page links to all 24 guides; the footer carries
both hubs. Breadcrumbs are rendered visibly and mirrored in `BreadcrumbList`.

Links in prose are generated through the same `href()` helper as everything else, so the deploy base
path is stated once. Nine hardcoded `/tman/...` links were removed in the process.

### 2.8 Head and accessibility hygiene — *fixed / verified*

- `robots` meta with `max-image-preview:large` and `max-snippet:-1` (opts into rich SERP previews).
- `theme-color`, `color-scheme`, `rel=alternate` to the GitHub releases feed.
- Exactly one `<h1>` per page; no heading-level skips; `lang="en"` on all 28; every `<img>` has
  `alt`. Tables scroll inside their own container so no page scrolls horizontally on mobile.
- Section headings carry `id` anchors, so SERP jump-links can target them.

### 2.9 Package metadata — *fixed*

`installers/npm/package.json` had no `keywords`, `homepage`, or `bugs`; npm search ranks partly on
keywords, so it was effectively unlisted for every term but its own name. `installers/python/
pyproject.toml` had no keywords, classifiers, or URLs. Both now carry them.

### 2.10 README — *fixed*

The README is the highest-authority page in this project and was a wall of prose with no navigation
surface.

- `# tman` → `# tman — supervise runaway test processes from AI coding agents`. The bare name ranks
  for nothing; a search for it returns a Unix manual command.
- Added a contents block (12 anchors, **all verified to resolve**), badges, an agent-compatibility
  table linking every setup guide, and a docs section pointing at both hubs by name.

## 5. Blocked: the root domain does not exist, so no `robots.txt` is servable

This is the most consequential finding in the audit, and it is not fixable from this repository.

**Measured 2026-07-29:**

```
https://standardbeagle.github.io/               404
https://standardbeagle.github.io/robots.txt     404
https://standardbeagle.github.io/tman/          200
```

`gh api repos/standardbeagle/standardbeagle.github.io` → **404, the repository does not exist.**
Meanwhile **eleven repositories on this account have Pages enabled** — `ageSchemaClient`, `agnt`,
`beagle-core`, `BifrostQL`, `brummer`, `caveman-mcp`, `mcp-tui`, `ps-bash`, `slop-mcp`,
`standardbeagle-tools`, and `tman` — all served from that one host.

Three consequences, in order of cost:

1. **No `robots.txt` can be served for any of the eleven sites.** Crawlers read it only from the
   domain root, and the domain root 404s. This is not a misplaced file; there is nowhere to put one.
   A `site/public/robots.txt` here would be served at `/tman/robots.txt` and ignored — which is why
   none was added. Shipping a file that looks like it works and does nothing produces no signal to
   act on, so it survives indefinitely.
2. **The host's front door is a 404.** Anything that resolves the bare domain — a crawler following
   a link that dropped the path, a human trimming the URL, a link-preview bot — gets an error page.
   That is a poor signal on the one URL every one of the eleven projects has in common.
3. **No place to aggregate.** Eleven projects share one host's reputation and there is no page
   linking them, so none of the internal linking between them that a crawler would use to find the
   others exists.

**The fix — create the `standardbeagle/standardbeagle.github.io` repository.** It needs one
`robots.txt` and one `index.html`:

```
User-agent: *
Allow: /

Sitemap: https://standardbeagle.github.io/tman/sitemap.xml
```

The `index.html` should be a short landing page linking all eleven project sites. That is a few
hours of work that upgrades the root from a 404 to a hub, and it is the single highest-leverage SEO
change available across the account — it benefits every project, not just tman.

Also outside this repository:

- Submit `https://standardbeagle.github.io/tman/sitemap.xml` to Google Search Console and Bing
  Webmaster Tools. Submission does not require the sitemap to sit at the domain root, so this works
  today, before the repo above exists.
- Consider a dedicated domain for tman. A subpath cannot be verified as its own property in Search
  Console, so today there is no way to see tman's search performance separately from the other ten
  projects — and with no root site, no way to see it at all.

### Deployment note

`.github/workflows/site.yml` triggers on pushes to **`main`** touching `site/**`. The pages in this
change do not go live until the branch is merged; `/tman/sitemap.xml` 404s until then, which is
expected and not a defect.

## 6. Product findings surfaced by this work

Three things about tman itself, found while writing and testing the integrations. None is an SEO
issue; all three affect whether the documented setups work.

1. **The hook requires `tool_name` to be exactly `"Bash"`.** Verified by probe: a payload with
   `"tool_name":"shell"` produces empty output and silent non-supervision. Codex CLI also names its
   shell tool `Bash`, so the shipped hook is directly reusable there — but Gemini CLI
   (`run_shell_command`), opencode (`bash`), and Antigravity (`run_command`) all differ, which is
   why those guides carry wrappers. Accepting a set of known shell-tool names, or a
   `--tool-name` flag, would remove three wrappers.

2. **The rewrite omits `permissionDecision: "allow"`.** Codex documents a rewrite as
   `permissionDecision: "allow"` *alongside* `updatedInput`; tman emits `updatedInput` alone, which
   is what Claude Code's contract asks for. Whether Codex applies the replacement without it is
   untested here, and the guide says so and gives a verification recipe rather than claiming it
   works. Emitting the field is likely inert for Claude Code and would remove the doubt.

3. **Command resolution does not check the executable bit.** `tman run -- env` failed with exit 127
   naming `/home/beagle/.local/bin/env` — a non-executable 328-byte file that a shell's PATH search
   skips and tman's does not. This is the same failure class as the `~/.local/bin/test` note already
   recorded in `.claude/rules/honest-failure-and-verification.md` §1, and it turns a working command
   into a confusing "permission denied" naming a file the user never installed deliberately.
